# Results

Generated by `tools/collect-results.sh report` from the files in
`build/results/`. Every harness gates on correctness before it
times anything: the kernel-compile figures are only recorded for
stages whose output image is byte-identical to the reference, and
the rest only for runs that reach the end-of-corpus sentinel with
zero failing cases.

Each engine is built several times with flags that move code
and change nothing it computes. Every build is timed; the
figure is the MEAN across builds, each build being the minimum
of several interleaved rounds, net of process startup. The ±
is one standard error of the ratio.

That structure is deliberate. The variation here is dominated
by per-BUILD bias rather than run-to-run noise: repeated runs
of the same binaries agree to 1-2%, but a rebuild moves a stage
by five or ten, and on this project the cell-engine BASELINE -
which divides every ratio below - had the widest spread of all
at 12.6%. Averaging runs cannot remove a constant; averaging
builds can, and the ± includes what is left.

Ratios travel between machines; absolute cycle counts do not.

Measured in CPU CYCLES, user space, from the hardware counters
(tools/cputime.c): independent of clock frequency, so of boost,
throttling and the governor - not in CPU time. User space only:
the kernel's part of a run is left out, and subtracting start-up
removes most of it (see tools/clockfit.py).

Figures below are the mean over 5 layout variant(s) per
engine. A single build gives a number that repeats to 1%%
and can be wrong by 12%%.

Measured on:

```

cpu: AMD Ryzen 7 PRO 8840HS w/ Radeon 780M Graphics
```

## The stages

- `sod32` - SOD32 (Benschop, 5-bit packed, 32-bit only)
- `s0-cell` - RelF cell threading
- `p4-pack4` - tagged nibble  (rejected 157, built here)
- `p8-pack8` - tagged byte    (rejected 157, built here)
- `s1-sod16` - SOD16  16-bit tokens + word table
- `s2-cpt16` - CPT16  table deleted, computed target
- `s3-cpt16f` - CPT16 + folded prim;EXIT
- `s4-cv8` - CV8    byte stream
- `s5-cv8spec` - CV8 + specialisations
- `s6-cv8b` - CV8 + byte-granular dictionary headers
- `s7-spn` - SPN on the cell image (frozen), recipes replayed at start
- `s8-spncv8` - SPN on the CV8 image, recipes replayed at start
- `s8-lazy` - SPN on the CV8 image, most words translated on first call

## Image size, bytes

The unit is the FORTH IMAGE - the smallest image that boots into
the interpreter and can rebuild the system - following SOD32's own
Makefile, where `forth.img` is the finished artefact. Shell images
are measured separately in `build/sizes-shell.csv`.

*run-only* images carry an identical word set at every stage, so a
difference between two rows is the encoding and nothing else.
*self-hosting* images also carry that stage's own emitter overlay,
which is what lets them compile their own encoding.

`p4-pack4` and `p8-pack8` rewrite the cell image in place and leave
the cells they skip where they were, so the FILE they produce is
stage 0's size. The *packed* column below is what the image
becomes once those cells are removed.

That figure is arithmetic, not an estimate and not a model. These
schemes are cell-granular: a pack replaces exactly N cells with one,
nothing changes alignment, and every reference in a RelF image is
relative. So compacting removes exactly (cells folded) x (cell size)
bytes and can change nothing else. A relocating build would
demonstrate the number; it would not alter it.
