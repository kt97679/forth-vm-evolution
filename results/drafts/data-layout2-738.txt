# The fixed data layout, step 2 - the return stack's top on the hot page (Iteration 738; queued: results/queued-layout2)

The owner (737): "proceed with step 2". Step 1 (Iteration 734, results/drafts/data-layout-734.txt) put the small
variables on a page of their own; every run also writes the top of the return stack, one page more. Step 2 makes them
one page: engine/vm-lab.c's stacks' chunk (STACKSEP, every role) is STK_PAD = 1024 bytes longer, the extra on the
return stack's side, so the chunk - still page-aligned - ends 1 KB into a page; engine/data-layout.ld puts it first in
.bss.hot and the small variables straight after it. The return stack's floor, the data stack's floor and the guard
pages stay on page boundaries (the six `STK_END - RSTACK_BYTES` became `... - STK_PAD`); the return stack is 1 KB
deeper. Without STACKSEP (the stacks at mem's top) STK_PAD is 0. lab/evolve/data-layout-check.py excepts stackmem in
.bss.hot. Not applied: it changes the memory reading, so seeds 97 on would not compare (ORDER.md: apply when the series
ends).

Built in a git clone of e198c8b3 (Iteration 737) - run-tests PASS, validate 7 of 7, data-layout-check --self-test PASS -
and measured against master by results/drafts/data-layout-734.py (BASE NEW; its tables keep step 1's title).

## The pad's size and alignment

1024: the kernel workload's return stack stays within it (under gdb at exit). The first trial (stackmem not
page-aligned, the offset by its placement) measured 512 and 2048 worse than 1024 and grew engines (portable-knee
+80 B). Page-aligned with the pad inside, as taken: no x86 byte.

## The stacks' traps (results/drafts/stack-traps-738.sh, both trees)

The ten roles' x86 builds (data-layout-734.py's dlay-ROLE) and the three clang ARM designs of
results/relf-designs-718.md (219878ec89, d727605472, 48a012411a; 4-byte cells, under qemu-arm): every program's
status and message the same in both trees - return stack overflow, data stack overflow, a runaway underflow of
either stack, 20000-deep recursion (the overflow trap), 25 FIB (75025). The guard designs say "data stack underflow",
the others "segmentation fault" from the fault trap, as before.

## ARM (tools/arm-cross-check.py results/relf-designs-718.md)

3 of 3 built, alive, fib and apps identical; each engine +4 B (6100 -> 6104, 12896 -> 12900, 18128 -> 18132). The
stacks' end, stackmem + 0x50400, is no longer one ARM immediate (0x50000 was): the VM's entry adds 0x10400 first, then
0x40000. Unavoidable with this layout - the return stack's floor must stay page-aligned and its top 1 KB into a page,
so some address the engine forms is always two adds from the chunk's base. A constant on every ARM engine, no ranking
moves. The ARM faults are not measured here (qemu-user's faults are its own); the Tegra can, and `#define STK_PAD 0`
under `__arm__` takes the bytes back if it shows none fewer (ORDER.md). The GCC ARM build (--gcc, the cross GCC) was
not run: the cross compiler is not installed now (ship-rehearsal-737.sh's order puts it in last).

## Found on the way, the same before and after: the JIT's code has no data-stack bound

On the three JIT roles without the guard gene (small-jit, fastest-x86-32, fastest-x86-64) `: OVF BEGIN 1 0 UNTIL ; OVF`
dies 139 with nothing on stderr. The interpreter checks dsp against g_dsp_limit; the JIT's compiled code does not, and
without a guard page the push runs down through everything below the stacks - under strace the first fault is at
0x3ffff8, just below the engine's first page: the tightened engine is one RWE segment, so its tables, data and code,
the fault handler's included, were overwritten on the way; the handler then faults (si_addr NULL) and the kernel kills
it. Iteration 151's symptom, back for JIT code alone - any output still buffered is lost. best-all-round (JIT and
guard) reports "data stack overflow" correctly. The owner's call (GOALS.md's register): the guard gene on those roles
(256-448 B, Iteration 251's price), a single PROT_NONE page below the data stack for JIT designs, a dsp check on the
JIT's loop back-edges, or leave it. `: DEEP RECURSE ;` on best-all-round and the JIT roles loops (124 at 20 s): the
tail call makes it a jump - by design.
