# The JIT at 32-bit x86 - a feasibility study, and a working prototype (Iteration 460)

The owner (459-460): start on the i386 port of the stencil JIT while seed 68 runs - the gap the c4 family pointed at
(results/drafts/c4-family-459.md): the JIT is x86-64 only, and a JIT design's 32-bit speed is its interpreted speed -
eval32() builds it "its JIT off" (Iteration 336), because spn-abi.h stopped any other x86: "SPN knows x86-64 and 32-bit
ARM".

## The method carries over

The JIT copies SPN's stencils - ordinary C functions in spn-stencils.c, compiled into the engine - back to back into
executable memory and patches their holes. Nothing in that is 64-bit at heart. What was, and what changed
(results/drafts/jit-i386-460.patch, 5 files):

- **The convention** (spn-abi.h): x86-64 passes the state (sp, tos) in rdi and rsi and returns it in rax and rdx; 32-bit
  ARM packs it in one 64-bit value, r0 and r1 both ways. i386 now does as ARM: one 64-bit value, and regparm(2) brings it
  in eax and edx, where a 64-bit return leaves it - so one stencil's output registers are the next one's inputs, which is
  what lets copied stencils run back to back. SPN_CC carries the attribute to the stencils, the markers
  (spn-markers.c) and the interpreter's call into native code (vm-lab.c).
- **The holes** (spn-stencils.c): x86-64's 8-byte literals by movabs; at 4-byte cells a mov $imm32 by inline asm, the
  values distinct as ARM's (0x5ea1ed01 to 04); IMM32 folds into instructions as before. jit.c finds and fills a cell's
  width - JIT_HOLEW, 8 or 4 - and skips endbr32 as it skips endbr64.
- **A real bug found on the way**: a variable called from a translated word became the literal align8(body + 5) - right
  at 8-byte cells, 4 bytes off at 4-byte cells, where the interpreter aligns to the cell (corpus: "SEEBUF -> 00 00 00"
  wrong; VARIABLE V 9 V ! : B V @ ; B . printed garbage). Now aligned to CELL_BYTES - unchanged at 64 bits.

## It works

s6 with the JIT's genes (engines-check's JIT variant: tag2, jit, jitx, jitloop, jitinl, jittail), built with
EVOLVE_CELL=4 and gcc -m32 -fno-pie -no-pie: built (19,436 bytes against 12,440 without the JIT), the corpus to its end,
its output line for line the same as the 32-bit engine without the JIT. Measured here against the 32-bit s6 (this
machine has one core - indicative only):

| workload | without the JIT | with it |
|---|---|---|
| kernel | 1.240 | 1.113 |
| fib | 0.772 | **0.330** |
| corpus | 1.182 | 1.197 |
| loop | 0.887 | 0.900 |
| bubble | 0.823 | 0.870 |
| ackermann | 0.924 | **0.592** |
| **speed (geometric mean)** | **0.956** | **0.767 (-20%)** |

Calls and recursion gain most, as at 64 bits; loop and bubble not here - the evolved designs' loop genes (rtloop,
rtloopall) are not in this variant.

## To make it real (proposed - the owner's call)

1. **eval32() keeps the JIT** where the design has it - its 32-bit speed then the JIT's; the fronts' "fastest at 32
   bits" will move, a break in that column to note.
2. **jitk off at 32 bits** until gen-jitk.py writes i386 variants (its register cache names x86-64 registers); jitret is
   x86-64 only already (#if).
3. **engines-check**: the JIT variant built and checked at 32 bits too (V32), so the tests guard it.
4. **dream's 32-bit build** (prebuilt32) measures front designs with their JIT; the Tegra stays without - ARM needs its
   own scan (branches are not E9 rel32; holes are movw/movt pairs, which spn-stencils.c already writes for SPN).
5. Then the 32-bit fronts' designs measured with and without - the JIT's gain at 32 bits on evolved designs, not on s6.

As the after-seed-68 batch, batch-checked as any. 32-bit ARM after: spn-abi.h and spn-stencils.c already know it; jit.c's
scan and patch would need ARM's branch and movw/movt forms.
